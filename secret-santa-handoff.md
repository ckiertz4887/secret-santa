# Secret Santa App — Handoff

## What this is
A static, single-page Secret Santa reveal app. No backend, no database — assignments
are generated once, encrypted client-side-compatible, and embedded directly in the
HTML. Each person gets a personalized link; visiting it decrypts *only their own*
entry in the browser using Web Crypto (AES-GCM), so nobody (including whoever hosts
the page) can read the assignments from the deployed file without a valid code.

## Constraints the assignment logic satisfies
Given a group of gifters/giftees, couples, and a prior year's assignments:
1. No one is assigned to themselves.
2. No one is assigned their partner.
3. No one is assigned the same giftee they had the previous year.

With this year's 8-person group (4 couples), there are **1,257 valid assignments**
out of 40,320 total permutations (4,752 if you drop constraint 3).

## Files
```
secretsanta/
├── generate.py          # Generates a valid assignment + encrypts it per-person
├── records.json          # Encrypted payload (name, salt, iv, ciphertext) — safe to embed publicly
├── codes.json             # Per-person plaintext codes — needed to build personalized links, NOT the assignment itself
├── PRIVATE_assignment_do_not_view.json   # The actual plaintext mapping — kept for verification only
└── index.html             # The full app — embeds records.json's contents inline

firebase-project/
├── public/index.html      # Same app, ready for Firebase Hosting
├── firebase.json
├── .firebaserc             # Needs your real Firebase project ID
└── README.md               # Deploy steps
```

## How the crypto works
- Each person's giftee name is encrypted with AES-GCM.
- The decryption key is derived from their personal code via PBKDF2 (SHA-256, 100,000 iterations, random 16-byte salt per person).
- The HTML page embeds ciphertext + salt + iv for all 8 people, but a given entry only decrypts with the matching code — wrong code fails the AEAD auth check, not just "wrong answer."
- No name-to-giftee mapping ever leaves the browser in plaintext.

## Personalized links
Format: `https://YOUR-DEPLOYED-URL/?n=<Name>&c=<Code>`

Codes are generated by `generate.py` and saved to `codes.json` (gitignored). Each person's
personalized link is printed to the console when you run the script.

These codes don't reveal who has whom — safe to keep, not safe to post publicly next to names.

There's also a manual fallback UI on the page (dropdown + code field) in case a link gets mangled or lost.

## Regenerating for a future year
Edit the `people`, `couples`, and `last_year` dicts at the top of `generate.py`
(`last_year` should be this year's *actual* results once revealed), then re-run:
```
python3 generate.py
```
This produces a fresh `records.json`, `codes.json`, and a new private assignment file.
You'll then need to re-embed `records.json`'s contents into `index.html` (currently
done via a `__RECORDS_JSON__` placeholder swap — see the bottom of `generate.py`'s
sibling embed step, or just re-run the same substitution pattern).

## Known limitations / open items
- No expiry or one-time-use on codes — anyone with a link can reveal that entry repeatedly.
- No admin view — whoever runs `generate.py` can technically open `PRIVATE_assignment_do_not_view.json` to see everything (by design, for verification), so full "even-the-organizer-doesn't-know" secrecy depends on not opening that file.
- Styling/design is a first pass (evergreen/parchment/wax-seal theme) — flagged as open to revision.
- Not yet deployed anywhere live; `firebase-project/` is packaged but `.firebaserc` still has a placeholder project ID.
